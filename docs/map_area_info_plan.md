# Map area information overlay — analysis and implementation plan

Research notes and an implementation plan for enriching the read-only tower map's per-area
information with the community **"Let It Die: Rotations and Resources Table V2"** data: the
materials found on a floor, the floor notes, stamp availability, the Yotsuyama Bionics / Tales
magazine collectibles, the wandering (secret) shop, boss drops and trap rooms — all of which vary
with the daily rotation.

Companion documents: `map_db_analysis.md` (what `masters.db` stores), `map_viewer_notes.md` (the
viewer's data mapping), `map_boss_plan.md` (boss/mini-boss overlay).

Labels used below: **confirmed** = shown directly by the source; **inferred** = purpose is clear
but not proven in-game; **unknown** = not enough evidence.

Sources, opened read-only:

| | |
|---|---|
| `Floor_data.html` | Google-Sheets export, the master per-area table (314 data rows) |
| `Current Rotation.html`, `Upcoming_ *.html` | the five weekday roster tabs (Wed/Thu/Fri/Sat/Sun) |
| `41-51F.html`, `NEO.html`, `TENGOKU (52F+).html` | endgame bands (out of the F1–50 scope) |
| `masters.db` | `D:\SteamLibrary\steamapps\common\LET IT DIE\BrgGame\Content\masters.db`, read-only |

The community sheet is by **Oberlinx & Kaito** (V2, February 2021), with original maps by
ZeroSplint/Kaito. Community data is not game data: it must be attributed and treated as dated.

> **Status: implemented (phase 1 + loot markers).** Shipped:

## 1. Answer in one paragraph

Yes, and the work splits cleanly in two. Most *mechanical* facts — material family, stamp slot,
shop slot, paid boss room — are already in `masters.db` and become automatically rotation-correct
if we read them on the placement row. The *human* facts — the free-text notes, the Yotsuyama
Bionics and Tales collectibles, the wandering-shop likelihood and the trap-room metal — exist only
in the community sheet. So the plan is: **import the sheet once into a committed JSON catalog**,
**join it to map nodes by `(rotation group, floor number, normalized area name)`** — a join that is
unique within every rotation and resolves for every in-scope node — and **render it as map badges,
list columns, tooltips and a details block**, with optional DB-derived material tiers/weights as a
secondary line. The only genuine risk was reconciling the sheet's rotation numbering with the
app's five templates; that is solved in §3 with 97–99 % measured precision.

## 3. Rotation reconciliation — the crux

### 3.1 The sheet's model

The `Rot` column holds eight ids. Two pairs are **byte-for-byte identical sets**:

- `rot1 == rot4` (30 rows), `rot3 == rot7` (31 rows) → confirmed.
- Effective distinct groups: `0`, `1(=4)`, `2`, `3(=7)`, `5`, `6`, and `B`.

`rot0` is the always-present base roster (72 rows). `B` is the fixed **Battle To The Top** band,
floors 41–51 (33 rows), present on every rotation. Each weekday layout is `rot0 ∪ B ∪ rot<day>`:

| Day | Sheet tab | Rotation group |
|---|---|---|
| Mon | *(not in download)* | `2` |
| Tue | `Upcoming_ Later` footer image is `LID_TueSat` | `3` |
| Wed | `Current Rotation` + tip "The Four Forcemen unleashed!" | `1` |
| Thu | `Upcoming_ Next` | `5` |
| Fri | `Upcoming_ Sooner` | `6` |
| Sat | `Upcoming_ Later` (`LID_TueSat`) | `3` |
| Sun | `Upcoming_ Later still` (`LID_WedSun`) | `1` |

Note: the sheet's `B` is the Battle-To-The-Top band and is unrelated to the app's template id
`B`. Keep the two concepts in separate names in code.

### 3.2 Mapping onto the app's five templates

The app shows five DB templates (`4HMA`, `A`–`D`) resolved from `master_area_template_term`. I
matched each template's DB node roster (floor number + localized `AREA_NAME`, stages MET/ARC/AMS/
RFT/HZM, floors 1–50) against each candidate `rot0 ∪ rotX` set. The winner is unambiguous
(precision = share of the candidate set the template actually mounts):

| App template | Sheet rotation group | Community layout name | Precision | Coverage |
|---|---|---|---|---|
| `4HMA` | `1` (`=4`) | Wednesday / Sunday | **0.971** | 0.744 |
| `D` | `2` | Monday | **0.990** | 0.761 |
| `C` | `3` (`=7`) | Tuesday / Saturday | **0.981** | 0.754 |
| `B` | `5` | Thursday | **0.990** | 0.759 |
| `A` | `6` | Friday | **0.990** | 0.752 |

The runner-up for every template scores ≤ 0.9. Two facts fall out of this and are worth surfacing
in the UI:

- The 12 rotating Four-Foreman floors (`Reginaka` 4F, `Omeno-Inari` 5F, `Kohni` 8F, `Fuga-Dokoro`
  12F, `Fune-Hashi` 14F, `Kyuzaka` 17F, `Hizashi-gaoka` 22F, `Hatake-gara` 26F, `Nabokucho` 30F,
  `Shirokin` 32F, `Dainoba` 35F, `Takanowa` 38F) are tagged `rot1` → **`4HMA` only**. This matches
  the boss plan's finding that the paid `*_SMALLBOSS` rooms are `4HMA`-only, and matches the
  "Four Forcemen unleashed" tip on the Wednesday tab. **confirmed**
- The app's `Today` shortcut selects a template, and the curated info then follows that template's
  rotation group automatically. **Correction (2026):** the term resolver originally picked the
  *next* upcoming `expires` boundary, which showed one day ahead of the game. `master_area_template_term`
  is a schedule of reset boundaries that *start* a term, so the shortcut now picks the most recent
  boundary (`map_db_analysis.md` §5).

### 3.3 Join key and coverage

For a selected template `T`, a map node resolves to the sheet row whose rotation set intersects
`{ "0", "B", TemplateRotation(T) }` at the same floor and normalized area name:

```text
normalize(name) = upper(replace(" ", "").replace("-", "").replace("_", ""))
resolve(template, floor, areaName):
    rows = catalog[(floor, normalize(areaName))]
    return first row where row.Rotations ∩ { "0", "B", TemplateRotation(template) } ≠ ∅
```

Measured against the installed DB (floors 1–50):

| Template | DB nodes | matched | unmatched DB nodes |
|---|---:|---:|---:|
| `4HMA` | 128 | 128 | 0 |
| `A` | 124 | 124 | 0 |
| `B` | 128 | 128 | 0 |
| `C` | 129 | 128 | 1 |
| `D` | 129 | 129 | 0 |

- **No `(floor, normalized name)` key is duplicated inside a single template** (0 collisions
  across all five). The pick is therefore deterministic — including for names that repeat across
  rotations (e.g. `Nokejiri` on 11F), because the rotations differ.
- Only three name/floor exceptions exist, handled by a tiny alias map:
  - `KO-ONI` (DB, 8F) → `Kohni` (sheet)
  - `NANBOKUCHO` (DB, 30F) → `Nabokucho` (sheet)
  - `DASAHI-MACHI`: DB 8F (`C`) vs sheet 9F — a genuine one-floor discrepancy; keep the DB floor
    number in the key and fall back to a floor-less name lookup.
- 7–9 sheet rows per template have no DB node (the Battle-To-The-Top extras on 41–51F and the
  alias names). They are ignored; BTTT 41–51 is partly outside the current F1–50 band scope anyway.

## 5. Proposed catalog format

A single committed JSON file (proposed `settings/map-area-info.json`, copied to the app output the
same way as `settings.catalog.json`), generated offline from the sheet. The app never parses HTML.

```jsonc
{
  "schemaVersion": 1,
  "source": {
    "name": "Let It Die: Rotations and Resources Table V2",
    "authors": "Oberlinx & Kaito",
    "updated": "2021-02-08",
    "note": "Community data; layouts verified against masters.db node rosters."
  },
  "rotationGroups": ["0", "1", "2", "3", "5", "6", "B"],
  "templateRotation": { "4HMA": "1", "D": "2", "C": "3", "B": "5", "A": "6" },
  "nameAliases": { "KO-ONI": "Kohni", "NANBOKUCHO": "Nabokucho" },
  "areas": [
    {
      "floor": 38,
      "name": "Ebata",
      "rotations": ["0"],
      "info": "",
      "material": "Aluminum",
      "stamp": false,
      "shop": "",
      "boss": "WE Red",
      "trap": "",
      "yotsuyamaBionics": null,
      "tales": "4.4",
      "notes": "BOSS: JIN-DIE. Drops War Ensemble Red Metal. Two Mk-5 Bullet Tubers."
    },
    {
      "floor": 5,
      "name": "Omeno-Inari",
      "rotations": ["1", "4"],
      "info": "44CE",
      "material": "×",
      "stamp": false,
      "shop": "",
      "boss": "",
      "trap": "",
      "yotsuyamaBionics": null,
      "tales": null,
      "notes": "BOSS: White Steel - Hard. Drops KC, WS Head / Legs / Spike Crusher BPs, and various Metals."
    }
  ]
}
```

Notes on the format:

- `rotations` keeps the sheet's ids verbatim; the app maps template → group at load. This keeps the
  import mechanical and auditable.
- `material` keeps the sheet's friendly value (`Iron`/`All`/`×`/empty). The exact DB families are
  derived separately at runtime, not stored here.
- `stamp` is a bool; `shop` is `"C"`/`"G"`/`"G★"`; `boss`/`trap` keep the sheet strings.
- `notes` is decoded text (HTML entities resolved). Rotation-conditional wording is shown verbatim.
- The file is small (≈314 rows) and diff-friendly; regenerating it is a one-command refresh.

## 6. Code plan

### 6.1 Core (`src/LidUtils.Core`)

New file `src/LidUtils.Core/MapAreaInfoModels.cs`:

```csharp
/// <summary>Curated, community-sourced facts for one floor area on one rotation set.</summary>
public sealed record MapAreaInfo(
    int FloorNumber,
    string Name,
    IReadOnlySet<string> Rotations,
    string Info,            // "" | "M" | "44CE"
    string Material,        // "Iron" | "All" | "×" | ""
    bool HasStamp,
    string Shop,            // "" | "C" | "G" | "G*"
    string Boss,
    string Trap,
    int? YotsuyamaBionics,
    string? Tales,
    string Notes)
{
    public bool IsRotationOnly => !Rotations.Contains("0") && !Rotations.Contains("B");
    public string ShopLabel => Shop switch { "C" => "Chokufunsha", "G" => "Gyakufunsha (may appear)", "G*" => "Gyakufunsha (always)", _ => "" };
    public string RotationLabel => ...; // "every rotation" | "Wed/Sun only" | ...
}

/// <summary>Loaded curated catalog keyed by (floor, normalized name) with rotation filtering.</summary>
public sealed class MapAreaInfoCatalog
{
    public static MapAreaInfoCatalog Empty { get; }
    public MapAreaInfo? Resolve(string templateId, int floorNumber, string areaName);
    public IReadOnlyList<string> Warnings { get; }
}
```

`MapAreaInfoCatalog` owns the template→rotation-group map and the name normalizer/aliases, so the
join rule lives in one testable place. `MapAreaInfoCatalogLoader.Load(path)` / `.Parse(json)` live
in `src/LidUtils.Core/MapAreaInfoCatalogLoader.cs` (alongside `SettingsCatalogLoader`) and use
`System.Text.Json`: no DB, no network.

Optionally add a `MapMaterialSummary` helper (Core) that turns `itemgenid` → families + tier range,
used for the secondary detail line; `MapDataService` would carry the raw `ItemGenId` on `MapNode`.

### 6.2 Data service

Two clean options; pick one when implementing:

1. **Resolve in the view model** (implemented): `MapDataService` stays DB-only. `MapViewModel`
   receives the `MapAreaInfoCatalog` (via `MainWindowViewModel` / `App`), and while building
   `MapAreaRow`/`MapNodeItem` calls `catalog.Resolve(SelectedTemplate, node.FloorNumber,
   node.AreaName)`. Keeps the bundled asset out of the DB service and makes the rotation join
   unit-testable without a database.
2. **Inject into the loader** (not taken): pass the catalog into `MapDataService.LoadAsync` and
   attach an `AreaInfo` property to `MapNode`, matching how `MapBossCatalog` already rides along.

Also add the optional DB material detail: read `master_floor.itemgenid` in `LoadNodesAsync` (it is
not read today) and expose `MapNode.ItemGenId` so the view model can render families/tiers when the
catalog has no material or the user wants detail.

## 7. Import pipeline

A one-off, non-shipped converter turns the downloaded HTML into the committed JSON:

```text
tools/import_floor_data.py  Floor_data.html  ->  settings/map-area-info.json
```

- Reuse the regex table parser (the export is a Ritz `waffle` HTML table, one `<tr>` per row).
- Decode HTML entities (`&amp;`, `&#39;`, `&nbsp;`), trim, drop the two header rows.
- Emit `rotations` from the `Rot` column, `stamp` from `●`, `shop` from the `Shop` code, and map
  `YB`/`Tales` to `int?`/`string?`.
- Do **not** bake in the template mapping at import time; keep the sheet's rotation ids so the JSON
  can be re-validated against the DB independently.
- Refresh procedure: re-download the sheet, re-run the script, review the diff, re-run the
  coverage smoke test. Record the sheet's update date in the JSON `source` block.

Attribution is mandatory in the UI: the details panel and/or footer should name the community
source and its date.

## 8. Phasing

1. **Catalog + join + detail surfaces** (lowest risk, highest value). Add the JSON, loader, catalog,
   join, details blocks, tooltip line and list columns. No map-drawing changes.
2. **Map badges + legend + `Loot` toggle.** Material ring/glyphs, stamp/shop/collectible markers.
3. **Farm filters.** Toolbar filters such as "only floors with Gyakufunsha", "only floors yielding
   <family>", "rotation-only areas". Optionally join to the save reader to mark Yotsuyama/Tales
   pages already collected ("missing here"), which is the natural follow-up since those
   collectibles are tracked per save.
4. **Endgame bands** (separate): Battle-To-The-Top 41–51F is already in the sheet (`rot B`) and can
   ride along; Heaven/Tengoku/NEO live in the sibling tabs and their own DB tables and are a later
   iteration.

## 9. Caveats, discrepancies and unknowns

- **Sheet age.** V2 is February 2021. The layouts were verified against the *installed* DB for
  F1–50, but the notes/collectibles are community-observed and may lag later balance patches.
  Surface the source and date; never present the notes as game data.
- **Material over-report.** On boss floors the DB defines an `itemgenid` group while the sheet
  marks `×` (no loose material spawns). Prefer the curated value; show the DB group as detail only.
- **Stamp mismatch.** 22/640 rows disagree; the disagreements cluster on band-boss floors, whose
  stamp machine is on a neighbouring area. Treat the curated flag as authoritative.
- **Name/floor exceptions.** `KO-ONI`→`Kohni`, `NANBOKUCHO`→`Nabokucho`, and the one-floor
  `DASAHI-MACHI` discrepancy. Keep a small, documented alias map plus a floor-less fallback.
- **`info` semantics.** `M` is inferred to mean "main-elevator floor"; `44CE` marks the rotating
  Four-Foreman floors. Not required for display (the DB already has elevator stops and FFM gates).
- **Rotation `B` vs template `B`.** Same letter, unrelated: sheet `B` is the fixed Battle-To-The-
  Top band, app `B` is a map template. Use distinct constants.
- **Licensing/attribution.** The sheet is community work; bundle it with credit and a dated source
  block, and keep the import script so the data can be refreshed rather than forked.
- **Unknowns**: whether any observed rotation-conditional note is still live in-game; whether the
  DB's `master_shop_appearance` `rate` (100 for the four rows) generalises; the exact meaning of
  `info = M`; and whether the four `44CE` boss names should be read from `master_gate` ids or the
  sheet's `BOSS` column when the two disagree.
